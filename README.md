# Pointer Remote

Native SwiftUI BLE pointer remote for iPhone and Mac (iOS 16 / macOS 13, Swift 5, no third-party dependencies). Both apps use a matching Material-inspired native theme: dark navy/charcoal surfaces, teal primary actions, violet secondary actions, rounded cards, pressed feedback, and visible text/status states. This is an app appearance only; it does not alter device brightness or auto-dimming.

## Hold pointer operation

Rebuild **both apps** after this protocol change. The iPhone pointer has a physical press-and-hold **Point** pad plus a separate ephemeral **Hold Lock** visibility latch:

- A `UILongPressGestureRecognizer` starts the physical hold after 0.2 seconds. A short tap on Point does nothing. The adjacent Hold Lock button is an ordinary tap control with a distinct locked state and an explicit Unlock label.
- Physical hold and Hold Lock are separate inputs to the same existing visibility intent. Releasing Point while locked stays visible. Unlock drops only the latch, so a finger still physically holding Point keeps it visible until release. Neither action starts tracking, recentres, rebaselines, resequences, changes settings, or adds a protocol message.
- Locking is accepted only for an active, foreground, approved, acknowledged tracking session with valid attitude state and no calibration, Recenter, recovery, or disconnect in progress. Unlock is always available while latched. A lock is never saved and never silently restored after launch, foreground, or reconnect. This also prevents a lock request from waiting on tracking startup and appearing after a later ACK.
- `.ended`, `.cancelled`, and `.failed` end only the physical hold. Background/inactive, view disappearance, approval loss, disconnect/Forget, Bluetooth or protocol failure, sensor failure, tracking stop, calibration, Recenter, and recovery force-clear both physical hold and lock. A late recognizer end is then harmless.
- Approval starts one acknowledged foreground **tracking session**. The phone then computes and submits motion continuously, including while the pad is not held. A hold changes only acknowledged visibility intent; press/release never resets the tracker, angle baseline, cumulative coordinate, sequence, selected display, or Mac logical target. Thus moving while hidden and then pressing shows the pointer at the new point. The selected display stays stable across presses. Its centre is used only on first initialization, when that display was removed, or by explicit Recenter.
- The iPhone uses processed `CMDeviceMotion.attitude` (quaternion plus rotation matrix) and native `gravity`, never raw two-axis rates. It requests `xArbitraryZVertical` without hardcoding the native matrix direction. At each Core Motion stream start, a pure helper compares both `M·gravityDevice` and `transpose(M)·gravityDevice` with reference down `(0,0,−1)`. It latches a direction only when one candidate is within 0.12 chord units (about 6.9°) and the other is at least 0.30 (about 17.3°) away. Identity and pure vertical-yaw poses are intentionally ambiguous: no motion or calibration sample is emitted, and the user is asked to tilt the phone top edge slightly toward the screen and tap Recenter. The latch survives Recenter/basis resets, clears on stream restart, and never switches per frame; a later chosen-direction gravity mismatch fails closed. The physical pointing axis is **+device Y: the phone's top edge**, preserving the old z-horizontal/x-vertical way of aiming. At a reference reset, forward is that transformed top-edge vector, down is measured gravity projected perpendicular to forward, up is its negative, and right is `forward × up`. Horizontal yaw and vertical angle come from the transformed top-edge direction using all three attitude axes. Roll about that direction does not move aim. This is an angle-to-screen mapping, not a screen-ray plane intersection, spherical display correction, perspective magnification, heading tracker, or drift cure.
- Extracted yaw/pitch radians are sent in fixed reference units using **420 units/radian**; Mac X/Y gains then independently convert them to points/radian exactly once. Each gain remains 80...16000 (default 420), rounded and stored together in `macPointerSensitivityPair`, with the existing legacy migration rules. Yaw is unwrapped across ±π. The named scalar-last quaternion is also checked against the native matrix in either possible rotation direction, so its convention is verified rather than assumed and q/−q remain equivalent. Aim near the reset basis's up pole (which is not always literal world vertical), gravity nearly parallel to the top-edge aim, invalid quaternion/matrix/gravity, or an implausible >90° one-sample discontinuity is rejected with a tilt/aim instruction instead of NaN or an arbitrary flip. Screen y is the negative vertical angle, so aiming upward moves the target upward.
- One generation-fenced `xArbitraryZVertical` stream spans idle tracking and calibration for an approved foreground connection. The tracking-start ATT acknowledgement captures the current extracted angle as the session baseline; there is no per-packet ACK. Background, disconnect, or approval loss stops tracking and hides. Foreground reconnection starts a fresh acknowledged session and safe angle baseline while retaining the Mac target. A sampling-rate change likewise stops and renews tracking. The same fixed 20-byte encrypted packet carries session `UInt64`, sequence `UInt32`, and cumulative x/y `Float32`; cumulative means angle displacement since tracking-session baseline, not integrated angular velocity. This continuous foreground sensor/BLE traffic costs more power than hold-only transmission.
- **Recenter** is the only normal action that centres the logical Mac target and refreshes the gravity-level basis. It ends the old tracking session, hides any active hold, waits for a fresh valid attitude/gravity sample, and sends an acknowledged epoch-fenced command. Only the matching status permits a new acknowledged tracking session and baseline, so stale 20-byte motion or visibility for the old session cannot undo the centre. Tracking then resumes continuously while unheld. A hold active at Recenter may require physical release/new hold to show again, but not to resume tracking. Epochs remain monotonic for the model lifetime; pending transport state survives sensor stop and clears only on matching status or real connection reset. Approval-loss unsent cancellation/disconnect fencing remains in force.
- Motion uses BLE write-without-response with exactly one replaceable latest packet; CoreBluetooth readiness resumes submission without a queue or per-packet retry. The Mac differences accepted cumulative coordinates, applies independent X/Y gain ratios once, and adds the delta to an **unbounded** logical target. It never clamps or edge-saturates. Outside the selected display the overlay hides, but overshoot remains real; enough reverse travel is required to reenter. Reentry shows while either physical hold or Hold Lock still supplies visibility intent; neither offscreen hiding nor reentry resets the session, basis, sequence, or target. An unlocked release outside merely hides and retains the target.
- The raw logical pipeline remains direct and latest-only: no perspective/spherical correction, deadzone, extrapolation, or frame backlog. The default-enabled Mac-only **Adaptive smoothing** switch applies a constant-memory 2D One Euro filter only between that latest logical target and the panel in visible display callbacks. It has no prediction or buffered playback, but can add visual tracking lag; turn it off for exact latest-only presentation comparisons. The panel is ordered only on a hidden-to-visible transition. Tracking has a five-second startup grace and a five-second accepted-packet lease; hidden valid packets renew it, while render frames and ordinary ten-second control heartbeats do not.
- The Mac receiver uses a fixed 880×660-point content area (4:3; outer titlebar chrome may differ), hidden/unified titlebar styling, and content-size resizability to prevent resizing. A 32-point header inset explicitly reserves native traffic-light clearance; this source-level change is unrendered and needs visual review. Its two-column layout keeps appearance, connection/trust controls, and bounded trusted-phone scrolling visible. Next to the size slider, a 220-point **Head preview (actual size; effects shown on pointer)** wraps the head renderer at 1:1 AppKit points; it is intentionally head-only and has no remote visibility, focus, or ordering effect.
- The Mac offers eight readable cases: Circle, Point Outline/Filled, Triangle Outline/Filled, Arrowhead Outline/Filled, and Plus. Both improved triangle styles share a sharp, narrow diagonal isosceles path with an approximately 22-degree apex. The arrowheads share a separate shaftless four-corner path with a true concave rear notch, making them visibly different from plain triangles. Outline shapes use a single chosen-color stroke; filled shapes use a clean opaque chosen-color fill. Safety margins keep every glyph legible and unclipped. The shape menu, native opaque sRGB ColorPicker, and 16–160 point size slider persist their values. A legacy saved `triangle` migrates to Triangle Outline, while existing `circle` and `plus` values remain valid. Size means the major glyph extent before stroke safety margin; the point glyph is 35% of that size. Changes redraw an active hold at its currently displayed centre without changing target or visibility.
- On macOS 14+, rendering uses the overlay window's `CADisplayLink`; macOS 13 uses `CVDisplayLink` for the stable selected display. The off-main bridge coalesces at most one main-thread frame. Links exist only while the in-bounds pointer is meant to be visible and are invalidated when hidden/offscreen, with generation fencing against late frames. A normal accepted frame filters only the latest logical target using actual callback monotonic uptime, then skips a redundant final `setFrameOrigin` on equality; begin, resize, display transition, and Recenter positioning are still forced, and fractional coordinates are preserved. The visual-only One Euro filter has no interpolation trajectory, prediction, or packet/frame queue; disabling it restores direct latest-only presentation on the next callback. The transparent nonactivating panel ignores mouse events and never moves the system cursor.
- Previous/next slide controls use filled triangular SF Symbols with large tap areas and VoiceOver labels **Previous slide** and **Next slide**. A light iPhone haptic acknowledges an accepted local tap; it does not confirm Mac delivery. Disconnected/unapproved/queue-rejected actions do not produce this feedback, and control retries do not repeat it. Haptic availability depends on the device/system.
- The timer's reset icon opens **Reset timer?** with **Cancel** and **Reset**. Confirming stops the timer and clears it to **00:00**; cancelling preserves the running/paused timer. Opening confirmation ends any pointer hold, and dismissing it never restarts pointer motion. Reset is disabled when the timer is already stopped and empty.

### Mac-authoritative appearance presets

The Mac owns six fixed appearance-preset slots. **Presets…** in Pointer Appearance can apply a slot, save the current appearance into an empty slot, explicitly confirm an overwrite, edit a slot name, or explicitly confirm deletion. Presets remain on the Mac when a phone is forgotten. A preset contains only pointer shape, opaque sRGB color, integer point size, Adaptive smoothing, Tail mode/lifetime/fade/scale-down, every existing Rope length/nodes/thickness/strands/gravity setting, and Gaming/rainbow-cycle settings. It deliberately excludes sensitivity, calibration, timer, approval/trust, peer identifiers, input/tracking sessions, sampling, logical target/display, Recenter state, diagnostics, and head position. Adaptive smoothing is included only as a visual presentation setting; selecting it does not claim to change motion mapping or BLE delivery.

The selected slot is truthful only while the complete normalized current appearance exactly matches that slot. Any manual Mac appearance/effects change that no longer matches yields **Custom** without autosaving. Applying a preset validates one complete snapshot before changing settings, writes the appearance preferences together through one model entry point, and resets only visual smoothing/decorative effect state. It does not recenter, restart tracking, change cumulative geometry, discard predecessor motion, or alter calibration/sensitivity. Apply/save/delete are unavailable during calibration and while jitter diagnostics is starting, active, or finalizing, so a diagnostics capture cannot silently change its recorded visual configuration.

The iPhone main screen remains non-scrolling and adds one compact Appearance menu plus **Save…**. It can select a slot or save the Mac's current appearance, but preset deletion is a Mac **Presets…** control. The phone never stores appearance locally or edits an appearance snapshot. After each approved connection it clears prior catalog UI, requests exactly one of the six slots at a time, and accepts only generation- and request-ID-matching application statuses. A selection label changes only after the Mac's semantic `presetSelected` acknowledgement—not after the ATT write callback. Save captures the Mac's current appearance at command-processing time. Occupied slots require overwrite confirmation; a stale catalog conflict returns the authoritative bounded existing name and requires a new confirmed request. Missing/unavailable operations remain connected and show Retry Sync rather than pretending success.

Preset commands use the existing encrypted, authorized, acknowledged control characteristic. Catalog replies contain one slot and one bounded name, never a full appearance JSON blob or six-status burst. Every page carries the authoritative nonzero state revision and selected slot; a mixed revision/selection restarts paging at slot 1 with a bounded two-restart limit. Mac-local changes emit a coalesced invalidation rather than periodic polling or heartbeat catalog bursts. The phone allows one application-level preset request at a time, retries once on a bounded semantic timeout, and fences late responses on connection/sync generation plus a model-lifetime nonzero request ID. During one authorization session the Mac retains the 16 most recent terminal select/save/delete outcomes in one shared cache: an exact duplicate replays its original status and revision before any current gate or catalog check; a changed payload or mutation kind for a retained ID is rejected without replacing that result. This is a bounded replay contract, not universal history: an evicted older ID is rejected rather than applied. ATT success means only transport acceptance.

Names are NFC-normalized, outer-whitespace-trimmed, nonempty single-line text with no control scalars, at most 32 Unicode scalars and 96 UTF-8 bytes. Slots are wire values 0...5. Persisted snapshots use strict typed JSON decoding: unknown modes/shapes, non-finite/out-of-range numbers, numeric Boolean coercions, and invalid Rope node budgets are rejected. One malformed slot is skipped without discarding other valid records. Both apps must be rebuilt and installed together for this protocol version; an old peer is unsupported and should fail with the existing actionable protocol-mismatch path rather than being treated as compatible.

### Guided calibration

From iPhone Settings, **Calibrate X and Y…** suspends ordinary tracking transmission and visibility, then starts an acknowledged, authorized control session. The same live three-axis angle extractor supplies snapshots without resetting between markers. The Mac displays Centre, Upper Left, Upper Right, Lower Right, Lower Left. Apply still persists both values as one validated pair; Cancel/failure leaves both unchanged. After the terminal status, ordinary tracking renews with a safe angle baseline at the retained unbounded logical target—never an unintended centre or historical rescale.

The centre capture is the baseline. For each axis independently, the Mac converts reference units to radians (`r = (capture - centre) / 420`) and computes a zero-intercept least-squares gain in points/radian, `g = Σ(r·targetDisplacement) / Σ(r²)`. It rejects insufficient motion, reversed/non-finite/out-of-range gains, or normalized RMS residual above 0.25. A valid result is shown on the phone as separate proposed X/Y values. Only explicit **Apply** persists and publishes the validated pair together in the one authoritative preference record; **Cancel** and every failure retain the previous values. This prevents independent axis updates in normal preference representation, but makes no fsync or power-failure transaction claim. Starts, captures, Apply, and Cancel are session/step validated and idempotent under bounded control retries, including an exact replay of an accepted final Lower Left capture. Normal holds and slide keys are suppressed during calibration. Background, disconnect, authorization/Bluetooth loss, Stop/Forget, display changes, and connection reset stop motion and hide the dedicated marker; stale statuses are session-gated.

See `PointerRemote/Shared/HoldPointerTestFixtures.md` for source-level attitude, roll, sign/wrap, independent sensitivity, direct-render, calibration, Recenter-race, coalescing, and cancellation fixtures.

## Main screen and Settings

- The iPhone remote screen intentionally contains no `ScrollView`: it keeps a compact named connection status, Settings gear, small clearly labelled Recenter control, flexible-height Point pad with its compact adjacent Hold Lock/Unlock control, triangular slide controls, and timer visible in an adaptive layout, including compact phones. The large slide-control dimensions are unchanged. Settings remains scrollable. Opening Settings releases only a physical hold; an intentional lock can continue because the approved foreground tracking state is unchanged. Dismissing Settings never starts or relatches either input.
- The gear ends an active hold before presenting a separate scrollable Settings sheet. It contains Mac discovery/selection, Search, Connect, Disconnect, Reconnect Automatically, and connection, motion, and permission explanations. Pointer sensitivity is configured and persisted only in the Mac receiver. Dismissing it never starts a hold and does not discard an approved BLE connection or timer state.
- The iPhone target remains portrait-only (`UISupportedInterfaceOrientations` contains portrait). It does not claim an unimplemented landscape sensor transform.
- Protected-preferences, PointerUI-port, and inactive-window-scene messages are OS diagnostics. The app neither changes private APIs/permissions nor claims to suppress or diagnose those messages.

## Connection and safety model

- No Wi-Fi, LAN, or Multipeer connectivity is used. The Mac advertises a BLE peripheral service using `Host.current().localizedName` when available, and the iPhone acts as a BLE central. A name is display-only, never authentication and needs no wire handshake.
- Select a named Mac before connecting. The iPhone prefers a nonempty advertised local name, then `CBPeripheral.name`, then that peripheral's short UUID. It binds the name to the selected/connecting peripheral, displays `Connecting to <name>`, `Connected to <name>. Awaiting approval`, or `Connected to <name>. Ready`, and clears that active identity on terminal reset so an old peer name cannot label a new peer. A saved name is only a Settings/reconnect cache. BLE pairing/transport encryption and the one-connection Mac approval are separate. The iPhone saves only that explicitly selected Mac peripheral UUID/name. Reconnect Automatically is enabled after that explicit connection and, on foreground, tries only the saved UUID using `retrievePeripherals` then UUID-filtered service discovery; it never selects or connects to an arbitrary advertised Mac. There is no background-mode claim.
- Hello, tracking start/stop, visibility, Recenter, key/timer, calibration, and appearance-preset controls use encrypted serialized BLE writes with response; the Mac answers each ATT request once. High-rate motion uses the encrypted write-without-response characteristic. The Mac rejects commands and motion from unapproved centrals. ATT success is transport acceptance only; correlated preset statuses acknowledge application semantics. Rebuild and install **both** apps for this matching protocol.
- On the Mac, an explicit approval can use **Remember this iPhone**. This persists only CoreBluetooth's locally supplied `CBCentral.identifier`, never a caller-provided string. A remembered subscribed iPhone's encrypted hello receives the single active authorization while Receiving is enabled, but pointer movement remains idle until a new hold. An existing active/pending phone is never taken over. This local BLE identity is not custom cryptographic attestation and can change after reset, reinstall, or re-pair; approval is then required again. Individual Forget and confirmed **Forget All iPhones** revoke session/approval state, hide the pointer, invalidate queued statuses, and pause receiving until the visible **Resume Receiving** action. Forget All removes only `trustedPhoneCentralIDs`; sensitivity and appearance preferences remain.
- Confirmed iPhone **Forget All Macs** disconnects and removes only `lastExplicitMacPeripheralID`, `lastExplicitMacName`, and `reconnectAutomatically`. It clears scans, delayed retries, queued controls, motion, calibration, Recenter, and approval/session state; sampling and presentation-timer preferences remain. Late callbacks are fenced and cannot restore the old record. A future connection requires explicit Search, selection, and Connect. Neither app action claims or performs operating-system Bluetooth unpairing.
- **Stop Receiving** hides/revokes and suspends all acceptance, including remembered phones, until **Resume Receiving**. A stopped/rejected status and Manual Disconnect suppress reconnect attempts. Lock/background ends a hold and cancels scans, setup/cancellation deadlines, connection retries, and stability work without erasing saved reconnect intent; foreground restores the idle timer/connection only and never restarts a hold. Each automatic saved-UUID scan is stopped after 8 seconds. A retrieved or discovered saved-peer connection has 15 seconds to connect, discover the required service/characteristics, and enable status notifications; waiting for a person to approve on the Mac begins after that setup point and has no app timeout. An expired automatic attempt cancels its connection and consumes the existing bounded episode of at most four exponential retries (1, 2, 4, and 8 seconds); merely reaching `didConnect` does not reset the budget. Protocol/capability mismatch and a rejected current tracking start stop automatically with an actionable manual-connect message. Explicit Search is also an 8-second scan, but ends with a friendly manual retry action and never creates an automatic scan loop. Explicit selection and Connect start a fresh episode. Any terminal callback for an explicit pre-notification attempt—including either connect failure or disconnect—plus setup timeout, service/characteristic failure, or notification-subscription failure durably disables the persisted auto-reconnect switch, clears live connection intent, and requires Search/select/Connect; the cancellation watchdog does the same. Only a connection that completed notification setup may use bounded retries after a later transient disconnect.
- Authorization clears on unsubscribe, Bluetooth loss, **Stop Receiving**, and heartbeat expiry. Notification backpressure is authorization-generation fenced: a successful newer status removes an older queued status, and Forget/Stop cleanup invalidates queued approvals. A central whose bounded 16-entry status lane or bounded 16-outstanding-control admission limit overflows is quarantined for that current notification subscription. CoreBluetooth peripherals cannot be forcibly disconnected by a peripheral app, so recovery is explicitly an iPhone disconnect/unsubscribe followed by a real resubscribe; a duplicate subscribe callback does not clear quarantine. The visual pointer does not require macOS Accessibility permission. Accessibility is used only to post the previous/next arrow-key events, which are ignored while permission is denied.
- After approval, processed attitude and motion transmission continue throughout the active foreground tracking session. Local release queues only hidden visibility and preserves baseline/session/sequence/pending latest motion. Background, disconnect, Bluetooth loss, approval loss, calibration, Recenter, and queue-full teardown stop tracking and hide. The Mac allows five seconds from tracking start to the first packet, then expires after five seconds without a valid packet even while hidden; ordinary heartbeats do not renew that lease. Expiry requires manual reconnect rather than an automatic loop.
- Ordered controls are bounded to 64 messages and 512 encoded bytes/the negotiated acknowledged-write length. Stopping removes an unsent same-session tracking start and visibility; if tracking start is in flight/acknowledged, stop is placed first. Release only coalesces visibility commands. Session zero is rejected. Motion remains exactly 20 payload bytes (about 2,000 payload bytes/s at 100 submissions/s, excluding overhead).
- iPhone Settings persists and publishes requested sampling, measured sensor samples/s, and motion packets submitted/s; Mac publishes valid motion packets received/s. Requested, measured, submitted, and received are intentionally distinct; selecting experimental 200 Hz can still measure or deliver less. Rate/status counters publish at most once per second. “Submitted” means handed to CoreBluetooth, not delivered. Each completed hold also retains one compact, scrollable iPhone summary (attitude sample count, sensor timestamp max gap/rejected samples, x/y mean relative angles, pending overwrites, and submissions); the Mac prints one local summary (accepted packets, sequence gaps, receive max gap, render-frame max gap). Receive max gaps are between accepted received packets, and sensor max gaps are between valid consecutive sensor timestamps; both exclude startup-to-first-sample/packet. These use compact counters/running sums, not packet logs or high-rate UI. Mean relative angle is only a diagnostic summary and is not proof that a device was stationary or that sensor bias caused drift; sensor timestamps and local callback/receive/render scheduling cannot establish cross-device latency without synchronized clocks. Sequence gaps indicate unseen sequence numbers and may reflect coalescing, not necessarily BLE loss; “submitted” means handed to CoreBluetooth, not delivered.

## Setup

Open `PointerRemote.xcodeproj` in Xcode 15 or newer (the macOS 14 SDK declaration for window-bound `CADisplayLink` must be available), select each application target, and set a signing team. Deployment remains macOS 13; that release uses the native `CVDisplayLink` fallback. An iPhone device is required for motion testing. The macOS target has App Sandbox disabled because it posts arrow-key `CGEvent` input events; review signing, notarization, and distribution policy. Accessibility is optional for the visual pointer and required only for those arrow-key controls.

## Final integration

The current protocol separates continuous tracking from hold-only visibility. Recenter changes only the app's logical overlay target; it does not warp or hide the macOS system cursor. Rebuild and install **both peers**. These changes were inspected textually, not compiled in this workspace. ## Final reconnect integration

Source review identified a stale cancellation marker after Bluetooth loss or a matching connection failure and missing saved-size write-back. The parent cleared the marker on those teardown paths, added manager/peripheral identity and disconnected-state checks on terminal callbacks, and persisted normalized size on load. Initial connection activity now follows the actual scene state. Repeated hello messages no longer reset the Remember checkbox. Settings scrolling was restored; only the main remote screen is non-scrolling. These final edits received textual inspection, not a fresh independent review or build.

On a physical iPhone, test cancellation while connecting, Bluetooth off/on before cancellation completes, and returning to the foreground before disconnect completes. If CoreBluetooth omits the terminal callback after cancellation, a 5-second foreground watchdog terminalizes only the matching manager/peripheral attempt, retires that central-manager realm, persists auto-reconnect off, and requires explicit Search. Normal terminal callbacks also retire their realm before a retry so a callback from the old manager cannot reset a replacement attempt. Replacement-manager `.unknown`/`.resetting` states are shown as initialization rather than “Bluetooth off” or a false disconnect-in-progress state; powered-off, unauthorized, and unsupported states are distinct. Discovered peripherals and selection are manager-realm-bound and cleared on retirement/reset/off, so a replacement manager never connects an object discovered by its predecessor. Scan/cancel/connect/retrieve operations are issued only while the current central reports powered on; `.unknown`, `.resetting`, and every non-powered state locally cancel scan deadlines and clear discovery/selection, delegates, queues, sensing, approval, and connection state without issuing a non-powered command. Peripheral discovery, subscription, and writes additionally require a usable connected peripheral, while local cleanup still occurs when an OS command is skipped. Connect failures and unexpected disconnects show a bounded phase plus NSError domain/code/localized description, without dumping `userInfo`. The model retains one attempt-scoped peripheral-delegate proxy and invalidates it before teardown; forwarded callbacks require the current proxy and attempt generation. These source guards narrow late-callback acceptance, but cannot prove universal callback provenance if CoreBluetooth delivers an already-queued operation callback to a newly rebound delegate. Manual Disconnect disables automatic reconnect until explicitly enabled again. For remembered approval, enable **Remember this iPhone** before pressing **Approve** on the Mac.

### User-initiated jitter capture

The Mac Connection box has a compact **Jitter Diagnostics…** sheet. While an approved continuous tracking session is available, **Start 20-Second Capture** records bounded local timing evidence; unavailable tracking is explained and does not create a fake zero report. The sheet can stop early and copies the finalized plain-text report with **Copy Report**. A completed report remains until the next capture starts. Adaptive smoothing is disabled for changes during an active or pending capture, and each report records the immutable capture-start setting and filter constants so on/off runs remain comparable. Disconnect, Stop/Forget, Bluetooth or tracking-session teardown, Recenter, calibration, display configuration change, and app termination finalize an active run so sessions are not mixed. A timer finalizes the 20-second run even if packets stop.

The Mac peripheral manager and every CoreBluetooth object/call now belong to one dedicated serial queue. Only decoded immutable values cross to the `@MainActor` model. A lock-protected one-slot cumulative-motion mailbox posts at most one main drain, while controls atomically seal the preceding motion snapshot so tracking, visibility, Recenter, gain, calibration, approval, Stop, and Forget boundaries cannot reorder or rescale old movement. Main-originated boundaries use a finite 32-intent typed queue: gain changes coalesce to latest axis values, while diagnostic finalization and display topology retain a bounded sticky representation under pressure. A confirmed Forget removes only its selected persisted trust immediately and fences older approval before asynchronous transport cleanup; queue overflow is not treated as confirmation. Overflow instead pauses/revokes authorization and quarantines every current subscription until a real unsubscribe/resubscribe, without deleting remembered iPhones. Hidden tracking still maps and retains the raw logical target. While visible, the default-enabled optional display filter may smooth only panel placement; it never changes mapping, sensitivity/calibration, lease, packet admission, diagnostics receive accounting, clamping policy, or rounding. It uses One Euro low-pass derivative then `cutoff = minCutoff + beta·speed` (shared XY speed in Mac points/sec), with `alpha = 1/(1 + tau/dt)` and `tau = 1/(2π·cutoff)`, sampled from actual callback uptime. The initial conservative, empirically untuned values are min cutoff 12 Hz, derivative cutoff 10 Hz, and beta 0.025 Hz per (point/sec); these are not measured latency guarantees. Long/invalid callback gaps reset to the latest target. Encrypted characteristic permissions and manual approval remain unchanged.

Receive observations use an independent serial-queue diagnostic accumulator with an authoritative start, fixed `start + 20 seconds` deadline, and half-open `[start, deadline)` admission. Its callback baseline begins inside the epoch, each eligible accepted candidate is counted before latest-coordinate mailbox coalescing, and Stop freezes the immutable serial snapshot in the serial stop/barrier operation itself. Bluetooth loss likewise freezes before transport clearing and delivers that one capture-ID-correlated partial result; it never substitutes a fake empty report. The serial cutoff is the observed stop/loss boundary capped by the fixed deadline, not a retrospective UI-event timestamp or an immediate real-time promise while Stop waits behind queued work. Main accepted-mapping/render attribution stops separately when main receives the frozen boundary payload and the report labels both observations. A mailbox batch crossing a boundary cannot contribute a post-cutoff suffix to serial counts. Rejected/unauthorized/duplicate decoded motion candidates are labelled separately. Main accepted-mapping batch drains/handoff ages and visible display callbacks are separate timelines, attributed by their own main execution times rather than represented as raw receive events. Actual render intervals use `ProcessInfo.systemUptime` sampled at visible main callback entry, not `CADisplayLink.targetTimestamp` or CV predicted/output time; hidden/restarted display-link segments reset the interval baseline. Each sample array is capped at 16,000 while totals and overflow counts continue. Finalization alone sorts/formats nearest-rank percentiles; absent samples are `n/a`. None of these local timestamps proves BLE PHY delay, radio loss, photons-on-screen timing, or cross-device age.

For comparison only, a user-observed baseline before this queue/mailbox change had a 104 ms maximum accepted-receive gap and a 37 ms maximum legacy predicted-render gap. Those values are observations, not causes, targets, or evidence about the radio/PHY.

These measurements describe local Mac receive and main-callback scheduling only. They cannot prove photons-on-screen timing, draw cadence, CPU/GPU cost, BLE interval, radio loss, removal of 100 ms radio gaps, or synchronized end-to-end latency. The optional visual filter is not a radio-gap repair and has no measured smoothing or latency claim. Actual callback intervals are separate from the older display-clock/predicted `maximumRenderFrameGap` console metric.

## Limitations

Independent source review confirmed the main/Settings separation and shared model lifecycle. The main screen's fixed sizing and capped status lines may crowd or truncate at very large accessibility text sizes; this has not been rendered or device-tested. Full connection status remains available in the scrollable Settings screen.

The attitude solution removes direct raw-rate integration and makes roll about the pointing direction invariant, but does not guarantee zero drift or world-absolute heading. Continuous foreground Core Motion and BLE transmission increase power use. Motion between delivered samples cannot be reconstructed. The logical target is unbounded; only overlay visibility is bounded to the stable selected display. The panel cannot promise presentation over protected system screens or every third-party full-screen mode.

No build, signing, simulator, physical-device, BLE pairing, Accessibility/TCC, overlay click-through, or synthetic-input test was run here. App termination requests the same serial freeze before transport invalidation, but process exit may prevent the asynchronously delivered report from being rendered or copied; no durable-at-termination report guarantee is made. The reported repeated connection failure and CoreBluetooth powered-state API-misuse log motivated this source repair, but the repair has not been device-verified. A later device report showed `CBErrorDomain` code 15, “Failed to encrypt the connection, the connection has timed out unexpectedly.” That is an OS BLE encryption-establishment/runtime failure distinct from the source state-command and manual-intent defects repaired here; this patch does not claim to resolve it, does not weaken encryption, and Pointer Remote's Forget action still does not clear operating-system pairing. CoreBluetooth behavior and display coordinates vary by signed hardware and OS version. The 8-, 15-, and 5-second values are dispatch scheduling thresholds, not real-time guarantees: suspension, main-queue delay, and OS Bluetooth scheduling can make visible completion later. Manager identity, realm identity, attempt generation, proxy identity, and current characteristic/object guards narrow ordinary stale-callback acceptance, but they are source-level defenses rather than absolute CoreBluetooth provenance or cached-object-lifetime guarantees. In particular, late ATT callback ordering and callback delivery to a rebound delegate were not tested on hardware.

## Presentation timer

The iPhone Settings sheet has a Timer section with **Count Up** and **Count Down**. Count Down stores a total whole-minute duration from 1 through 180 (default 10). Its optional warning is explicitly **after N elapsed min** (default 8 for the 10-minute default), so “8 of 10” means two minutes remain. A one-minute countdown disables the warning. Timer settings are persisted as validated discrete values; malformed values normalize on launch. To prevent an in-progress discontinuity, timer settings can only change before a run or after Reset.

The countdown uses the existing one-second foreground UI timer and a monotonic elapsed-time base, so pause/resume retains accumulated active time. It displays remaining time with ceiling semantics, starts at the full duration, stops at zero with **Time is up**, and Start after expiry begins a new full countdown. Reset asks for confirmation, stops the timer, returns Count Up to `00:00` or Count Down to its full duration, and rearms milestones. A foreground tick that crosses both a warning and expiry emits only expiry.

Timer alerts create **no sound**: no audio player, system sound, audio session, notification scheduling, sound resource, or audio event is used. On hardware supporting Core Haptics, the fixed warning is two haptic-continuous events: 0.3 seconds at time 0 and 0.3 seconds at time 0.5 (a 0.2-second gap). Time-up is one intense three-second haptic-continuous event (intensity 1.0, strong sharpness). These patterns are not configurable. The engine is configured `playsHapticsOnly`; unsupported/failed haptics show an honest Settings status and have no audible fallback. Pending players are stopped and generation-fenced on reset, pause, background, configuration change, and new run. Haptics are requested only while the app is active; on foreground the timer recomputes immediately and may issue at most the currently relevant missed milestone (expiry has priority). Haptics can be disabled/unavailable, and physical actuator behavior is not guaranteed. Idle-lock suppression applies only while active; timing is not real-time.

See `PointerRemote/Shared/HoldPointerTestFixtures.md` for deterministic countdown transition fixtures. The compact visual layout, Dynamic Type/VoiceOver behavior, build, and actual haptic patterns were not run in this workspace.

### Durable connection incident diagnostics

Both apps keep a deliberately small, low-frequency connection incident history so a fleeting CoreBluetooth status is still available after automatic reconnect or relaunch. The iPhone history is in **Settings → Connection Diagnostics**; the Mac receiver has a **Connection Diagnostics…** sheet. Each surface supports full scrolling/text selection, **Copy Diagnostics**, and an independent **Clear** action.

Storage is bounded to the newest 16 incidents and 2,048 characters per incident (about 32 KB for typical text, but not a byte guarantee) in a dedicated `UserDefaults` record. Disconnecting, changing receiver mode, resuming, and automatic reconnect do not clear it. “Forget” actions remove only remembered peer approvals/selection and do not erase diagnostics or unrelated preferences. Clear removes only the diagnostic record; on iPhone, callbacks observed afterward are recorded as new incidents. The Mac Clear action also fences pending asynchronous snapshot completions.

The iPhone records wall time and local monotonic uptime, setup phase, bounded NSError domain/code/localized description, whether a terminal callback matched an application cancellation and its pre-cleanup reason, the payload-free in-flight control case and response age, queued-control count, tracking acknowledgement state, and last motion-submission age. It does not store Mac names/identifiers, message or motion payloads, or NSError `userInfo`.

The Mac records separate local trigger and serial-snapshot observation times; the latest raw serial valid-candidate uptime; separate latest main mapping execution time; outstanding/oldest retained controls; pending status-lane count; generation availability; and whether the motion lease was in startup or steady state. Serial-owned values are copied as an immutable numeric snapshot on the transport queue and delivered asynchronously to main; main does not synchronously read transport state. A generation mismatch is reported as unavailable rather than as zero.

These records identify local source paths such as OS terminal callbacks, application cancellation, Bluetooth reset/unsubscribe, authorization watchdogs, bounded queue quarantine, and local raw-arrival versus main-drain backlog. They are not packet captures and cannot prove BLE radio loss, end-to-end latency, remote-host causation, or what appeared on screen. No extra Bluetooth messages are sent, and connection policy, timeouts, security, and wire protocol are unchanged.

### macOS visual effects

The Mac receiver’s **Effects…** sheet offers Off, a smooth conservative quadratic Trail, or Rope tails and an independent Gaming rainbow (including the visible head). All existing lifetime/fade/scale, length/nodes/gravity/thickness/strands, movement-turbulence, and rainbow-cycle controls remain available. Turbulence is 0–100%, defaults to **0%/off**, and is included in Mac-only appearance presets; older preset snapshots missing that field migrate to 0%, while a present malformed value rejects only that record. Settings edit a local draft and publish only once through **Apply**; Cancel discards the draft, and applying is rejected if jitter diagnostics started while the sheet was open. The fixed-height sheet scrolls its controls rather than changing the main layout. This removes the prior synchronous whole-model control write and published-property self-normalization route, but without a crash report or runtime reproduction it is not proof of the reported Effects/Rainbow spin’s cause or resolution.

Effects run only from the already displayed pointer on actual display-link uptime, never predict or alter the head, remote mapping, or Bluetooth data, and are cleared while the overlay is hidden. Trail samples retain their original timestamps, expire by configured lifetime, and are rate-bounded without blindly dropping the oldest lifetime coverage. Rope uses a compliant XPBD distance chain. Each strand has a deterministic persistent screen-horizontal root offset centered around the exact displayed head (one strand is zero); adjacent roots are at least stroke width plus a small gap apart, with a 192-point total-span bound. Wide/eight-strand roots can therefore extend beyond the glyph intentionally. The glyph itself remains exactly at the displayed head, independent of these decorative anchors. Initial chains point predominantly screen-down with only a slight offset-derived fan, so stationary strands remain distinct rather than relying on an initial radial burst.

Decorative substeps interpolate only the root base from the preceding displayed sample to the current one; every constraint solve, safety pass, and final node-zero pin uses that strand’s offset root. Simulation advances at no more than 1/120 second per step and at most four steps, discarding older elapsed time. Post-solve damping is time-consistent and axial (10/s horizontal, 4/s vertical): horizontal whip remains strongly damped while screen-down gravity can settle visibly. Gravity is a screen-axis decorative acceleration, not a material claim; 0 is neutral. Motion turbulence is a bounded deterministic two-sine force with per-strand/node phase, applied only to non-head nodes. Its head-speed envelope is guarded by actual callback elapsed time and decays when stationary, so 0% preserves prior behavior and it cannot jitter or lag the pointer head. Existing finite velocity and radius guards remain. Node mass, compliance, iteration count, and the single 1.8× segment-stretch abnormal-state safety pass remain unchanged. Anchor/envelope/time history and chains clear on configuration, hide/recenter, offscreen, and long-gap resets. Global CG head/effect geometry unions all finite points into the transparent AppKit panel (including negative display origins); decorations remain capped to 1,024 points per axis from the true head, with the offset budget included in rope safety radius. No screen capture or fullscreen image is used. These are engineering choices, not runtime validation or proof of the report that gravity appeared weak.

The 220×220 appearance reference is deliberately a static head-only preview. Its label says effects are shown on the pointer; no animated preview is claimed. Trail/Rope/Gaming settings are saved locally and are preserved by Forget actions.
